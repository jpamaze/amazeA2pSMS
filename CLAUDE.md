# Notes for Claude sessions

- Design source of truth: the "New SMS Platform Blueprint" doc (https://claude.ai/artifact/RDYoq6GNjNSiNxBPLDJWCj) and `docs/`.
- Launch scope: India only with full DLT; HTTP and SMPP for both customers and vendors; no postpaid. Wallet + credit limit (default 0); resellers set sub-account limits within their own available balance.
- Delivery when the session cannot push: commit on `main`, then `git bundle create <scratchpad>/amazeA2pSMS.bundle HEAD main` (include HEAD) and send the file. The user saves it as `D:\ZAPIM\SMPP\amazeA2pSMS.bundle` and applies it to `D:\ZAPIM\SMPP\amazeA2pSMS` with `scripts\sync-from-bundle.ps1`. Give Windows/PowerShell commands with those paths.
- Commit author: Jaiprakash Khowal <jp@amazesoftwaretech.com> (set with `git config user.name` / `user.email` before committing).
- Tests: `go test -race ./...` needs Redis on localhost:6379 and Postgres `sms_test` (wiped each run); they skip when unreachable.
- Full stack without Docker: `scripts/dev-local.sh up|load|down` (in-memory Kafka via `cmd/devkafka`, vendor `cmd/smpp-sim`). Phase status and test results: `docs/phase1-core-messaging.md`, `docs/phase2-billing.md`, `docs/phase2-deals-disputes.md`, `docs/phase3-dlt.md`, `docs/phase3-network.md`, `docs/phase4-portals.md`, `docs/phase5-ha.md`, `docs/phase5-security.md`, `docs/soak-test.md`.
- User documentation: `docs/admin-guide.md` (portal), `docs/setup-guide.md` (production install), `docs/api-reference.md` (HTTP and SMPP for customers). Keep them in step with UI, deploy and API changes.
- Portal: `portal/` (Next.js static export). Build with `cd portal && npm ci && npm run build` before `dev-local.sh up` so admin-api serves it on :8081. Check UI changes with a headless Playwright walkthrough (install playwright in the scratchpad, not the repo; Chromium is at /opt/pw-browsers) and look at the screenshots. Wrap pages limited to some account roles in `Gate` (components/Shell.tsx) so other roles never call their APIs.
- Dev portal users (devseed): ops@amaze.local (platform), owner@demo-reseller.local (reseller, brand BlueText SMS), owner@reseller-shop.local (its sub-account), owner@demo-customer.local (direct customer).
- Dev DLT data: devseed registers PE 1101234567890123456, header AMZTST and templates `Your OTP is {#var#}. Do not share it with anyone. -Amaze` (smpp-load's default) and `Test message {#var#}`; any other text to the demo customer is refused (dlt_template).
- Kill dev processes by exact PID (`pgrep -x name`), never `pkill -f <pattern>`: the pattern matches the calling shell and kills it.
- Start Redis outside the repo (`cd /tmp && redis-server --daemonize yes`) so dump.rdb is not written here.
- Before building a bundle, `git fetch origin main` and build on top of it so the user's pull fast-forwards.
- HA rehearsal: `scripts/ha-local.sh up` (PostgreSQL/Patroni/etcd/pgBackRest, Redis/Sentinel, ClickHouse x3/Keeper, HAProxy, moto S3), then `eval "$(scripts/ha-local.sh env)"; scripts/dev-local.sh up`, `scripts/ha-drill.sh all`, `scripts/ha-restore-check.sh`. Tools: `apt-get install pgbackrest haproxy etcd-server etcd-client gettext-base`; Patroni in a venv outside the scratchpad (`/opt/patroni`, the postgres user must read it; `PATRONI_BIN`); ClickHouse static binary from the GitHub release (`CLICKHOUSE_BIN`); `moto[server]` (`MOTO_BIN`). Everything runs on one box, so latency there is CPU-bound, not representative.
- Vendors: one `connector` process runs every vendor (`VENDOR_ID=*`), starting, restarting and stopping them as the portal changes them (rescan 30 s, 5 s in dev-local) and creating their route topics. Report dates take `?tz=` (IANA, default UTC); the portal's selector is in `portal/lib/tz.ts`.
- Money in two stores: any code that changes a balance in PostgreSQL and Redis must run inside `wallet.Shared` (see `internal/billing/wallet/lock.go`), or `wallet-resync` can race it.
- Security: `APP_ENV` defaults to `production`; anything dev-only (header sign-in, the dev secrets key, private webhooks) needs `APP_ENV=dev` explicitly. Customer-chosen URLs go through `webhook.NewHTTPClient` (public addresses only). Run `staticcheck ./...` and `gosec` before committing security-relevant changes; govulncheck runs in CI only (vuln.go.dev is blocked from these sessions).
- Soak tooling: `smpp-load -interval 5m -reconnect` for long runs (fixed-size latency histogram), `soak-report` judges a run from Prometheus. The dev stack's in-memory Kafka keeps every record, so local soaks must stay short (500 TPS for 40 min is fine on 16 GB), and seed enough balance (`SEED_ARGS="-balance 100000000"`).
